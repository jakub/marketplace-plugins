# marketplace-plugins - how to work in this repo

This is jakub's Claude Code plugin marketplace (README.md is the user-facing tour). The repo root holds the marketplace manifest at `.claude-plugin/marketplace.json` (marketplace name `jakub`) and shared docs; everything else is a self-contained plugin under `plugins/`. Install strings are `<plugin>@jakub`.

The charter you already have in context says how we build. This file is only about what's specific to editing the plugins themselves.

## Versions and publishing

Each plugin has one version, written in up to three places that must agree: `plugins/<name>/.claude-plugin/plugin.json`, its entry in the marketplace manifest, and `plugins/<name>/.codex-plugin/plugin.json` when the plugin ships one. The marketplace entry is the number that matters, because both plugin managers name the cache directory after it. The description is mirrored across the same files and checked the same way: a marketplace listing and an installed manifest that describe the plugin differently is drift a reader hits before any code does. A Codex manifest exists only where Codex needs it, for a `hooks` or `mcpServers` pointer; a skills-only plugin (grill) has none, since Codex discovers `skills/*/SKILL.md` on its own. There is no catalog version. `scripts/smoke-plugin-manifests.mjs` asserts those mirrors agree, that a plugin with Codex hooks or an MCP server carries a Codex manifest, and that every hook script both `hooks/hooks.json` and `hooks/codex.json` point at exists.

Installs pull from the pinned GitHub clone, never from this working tree. To test a change: commit, push, then `claude plugin uninstall flow@jakub && claude plugin install flow@jakub`. Hook scripts can be exercised without a reinstall - `echo '<json>' | node plugins/flow/hooks/scripts/no-backlog-guard.mjs`.

Desktop and claude.ai bridge sessions load plugins from service-pushed snapshots with hooks stripped, so a bridge session never sees the charter or the guards; don't debug "the hook didn't fire" from one.

Adding a plugin: `plugins/<name>/` with a `.claude-plugin/plugin.json`, plus an entry in the manifest's `plugins` array with `"source": "./plugins/<name>"`. Plugins don't reach into each other's files - flow's prep stage uses `grill-with-docs` when it's installed and falls back to an inline grill otherwise, and that one-way, soft dependency is the model.

## flow

`plugins/flow/charter/charter.md` is hand-authored by jakub and is the source of truth. It is one file in two halves, separated by one marker line (`<!-- flow-charter: seat rules. ... -->`). Above the marker is doctrine for the orchestrator; below it (`## Rules of Engagement - Everything Else`, `## Seat Contract`, `## Gripes`) are the rules every seat follows. `hooks/scripts/inject-charter.mjs <session|subagent> <claude|codex> [1|2]` is the one injector on both hosts, and the whole file arrives at SessionStart wrapped in `<flow-charter>` tags, which the global CLAUDE.md checks for. Claude runs it as two SessionStart hooks because Claude Code caps one hook's stdout at 10,000 characters and swaps anything larger for a 2KB preview plus a file path; the injector cuts the file at the `## ` heading nearest the middle and prints a warning line if either half passes 9,000. Keep each half under that, or the session silently runs on a fragment while the presence check still passes. Codex takes the whole charter in one SessionStart write. SubagentStart on both hosts hands a spawned seat the seat half as `hookSpecificOutput.additionalContext`, skipping `Explore` and `fork` on Claude alone: Explore only locates files, and fork already carries the session's context. `lib/charter-payload.mjs` owns the marker, `splitCharter`, `seatPayload`, `sessionHalves` and the byte budgets. The charter is prose to a capable colleague, and it should stay that way. Every line costs context in every session, so anything that isn't true in every session goes somewhere else.

The orchestrator picks the model and effort of every seat from the charter's rankings table and its `## Rules of Engagement - Model Selection` bullets: match the seat to the hardest decision left in the task, and decorrelation is the family line. Nothing outside the charter names a model. `scripts/smoke-charter-conformance.mjs` is the lint, about 170 lines: exactly one marker, each required heading on the side of it that reaches the right reader, no role marker survives anywhere under `skills/`, `agents/` or `commands/`, no host binding directory under `charter/`, what the real injector prints in all four modes held under the caps, `Explore` and `fork` skipped on Claude and still delivered on Codex, and the delegated preamble equal to the seat half byte for byte. Its negative cases are inline strings, so a green run also proves it can fail.

Flow's shared `lib/hook-policy.mjs` owns protected-file, publication and merge policy; Claude and Codex adapters own their different tool inputs and output decisions. Never return Claude's publication `ask` result to Codex: Codex CLI treats that unsupported value as a hook failure and lets the command continue (observed on 0.149.1, still true on 0.152.0), so its adapter must deny and direct the human to publish manually. If a later Codex gains `ask` support, that adapter can retire.

`agents/implementer.md` keeps only the claims a Claude seat can make. The rules a seat follows come from the charter's seat half through the SubagentStart hook, so no agent definition carries a copy and there is nothing to keep byte-equal.

Doctrine lives in two places and no more. The charter holds what must be true in every session; the stage bodies hold the steps a stage executes. If something appears in both, delete one copy. The skill under `skills/flow/` holds what neither needs at runtime: setup, the doc stack, the ambient crons and hooks, the label contract, and the drift audit.

### Stages

All three pipeline commands are stages, and each stage is one file: `skills/prep-stage/SKILL.md`, `skills/issue-stage/SKILL.md`, `skills/land-stage/SKILL.md`. The body is host-neutral prose that names no host, no host-only tool, and no model, effort tier or role: it describes the shape of a seat and lets the orchestrator pick. It ends with a `## Host mechanics` section holding exactly two subsections, `### Claude Code` and `### Codex`, and those carry only what genuinely differs and is not already in the charter's `## Hosts` section, such as where the argument comes from, how a running seat is reached or that it cannot be, and what the escalation ping is.

`commands/prep.md`, `commands/issue.md` and `commands/land.md` are thin aliases: frontmatter with the tool allowance, one heading, one sentence pointing at the skill and `$ARGUMENTS`. Codex ignores a plugin's `commands/` directory, so there the human names the plugin-namespaced `prep-stage`, `issue-stage` or `land-stage` skill; `agents/openai.yaml` beside each sets `allow_implicit_invocation: false` because a stage that merges, opens issues, or spawns write seats must never start itself, though that suppression is unverified on the plugin-loader path and the human is the actual gate.

`scripts/smoke-stage-conformance.mjs` finds stages by structure (every `skills/*-stage/`) and checks, per stage: the frontmatter keeps model invocation off, the host-mechanics section has exactly the two subsections with prose under each, the body above it contains no host word, the Codex metadata keeps implicit invocation off, and the alias is the one-sentence shape with an allowance line. Its negative cases are inline strings, so a green run also proves the checker can still fail. There is no fixtures directory.

### Executors and guards

The merge is a deterministic executor on both hosts, not a checked command. `.flow/managed` is a committed marker that opts a repository into flow's merge enforcement; in a repository that has one, `publish-guard.mjs` and `publish-guard-codex.mjs` both deny every merge command they can recognize, through the same `mergeDenialFor` in `lib/hook-policy.mjs`, and name `scripts/land-merge.mjs` in the denial; in a repository without one neither guard gates a merge at all. The executor takes a pull request number and the head SHA the stage's gates ran against, and nothing else; its authorization is the human's explicit land request plus the stage's passed gates. It derives the host-qualified repository from the origin remote, reads the head SHA, state, draft flag and base branch from GitHub, refuses if GitHub's head is not the one it was handed (the PR moved after the gates), refuses armed auto-merge or merge-queue states, and runs `gh pr merge` from an argv array with `--match-head-commit` pinned to that verified head. The guards' command classification is a coarse tripwire whose only real requirement is that it never matches the executor's own invocation, and `scripts/smoke-release-path.mjs` asserts both halves against throwaway repositories with a fake `gh` injected in process.

Claiming an issue is the pipeline's other deterministic executor, `scripts/issue-claim.mjs`. Two issue-stage runs on one issue both see a green re-read of the assignment and the label, so keeping them apart is a tag push decided server-side. The helper creates `refs/tags/flow-claim-issue-<N>` on origin without force, and git's ref advertisement lets exactly one racer create it. It reads the porcelain flag column and not the exit code, because pushing at a tag that already points at the object you were about to push also exits 0, and that is the ordinary shape of losing this race. `scripts/smoke-issue-claim.mjs` races it against a bare repository under `mktemp` - no network and no fake git, since the guarantee is git's own and faking it would test nothing. The `claim` verb composes acquire, the live-run scans, the worktree and branch at the verified base, the push, the assignee and label move, and the release into one command that prints one JSON line; `scripts/smoke-issue-claim-verb.mjs` drives it against a bare origin with a fake `gh` injected in process.

`scripts/land-gates.mjs` is the land stage's read-only gate executor: it re-derives every fact the gates inspect (PR state, default-branch base and stacked children, the CI rollup partitioned with the base branch's known-flakes allowlist, every review thread over paged GraphQL, linked-issue recovery, the follow-up draft, auto-merge and merge-queue arming) and prints a JSON verdict with `stops` and `attention`. It mutates nothing; the rerun valve, the follow-up ack, child retargeting and the merge stay with the stage. `scripts/smoke-land-gates.mjs` drives it against a fake `gh`.

`scripts/tree-snapshot.mjs <path>` prints the four digests the prep and issue stages compare around every read-only seat (porcelain status, unstaged diff, staged diff, and every untracked unignored path by name, type, mode and content).

The git guard has two modes. Interactive mode denies the hook-bypass flag, trailers, bare force-push and the narrow destructive set, matched with quoted strings and heredoc bodies stripped. Cron mode (`FLOW_CRON_JOB` in the env) is a fail-closed grammar over every command; `skills/flow/cron/lint.md` states it and `hooks/scripts/git-guard.mjs` is the source. Two rules bind an edit: a call is one command, so `;`, `&&` and `||` are denied whatever they join, because a job's allowlist is a prefix over the whole string; and do not go back to a scanner that blanks what it recognizes, because two review rounds found eleven ways past one. The executor binds the repository path to a direct child of `FLOW_WORKSPACE`. Both modes have their own cases in `scripts/smoke-git-guard.mjs`.

The scheduled jobs are three files each: the prompt in `skills/flow/cron/<job>.md`, the allowlist in `scripts/flow-cron.mjs`, and the unit pair in `skills/flow/templates/systemd/`. A job's authority is the allowlist plus two mechanisms, never the prompt: git-guard's cron mode and `scripts/lint-actions.mjs`, the deterministic executor that alone performs the lint's worktree, branch, and label mutations after re-deriving the safety conditions from fresh state, with the two label verbs a claim could race holding the issue's claim tag through the claim executor's own acquire and abandon (`scripts/smoke-lint-actions.mjs` drives its verbs against a bare origin under `mktemp` with a fake `gh` on `PATH`; the git side is real); widening what a job may do is an edit to `flow-cron.mjs` and a version bump, and the prompt's "standing permissions" paragraph must match it. The report is the last main-thread assistant message starting with `# flow `, not the session's final message, and `scripts/smoke-flow-cron.mjs` holds that. Test a prompt change without installing anything: `CLAUDE_PLUGIN_ROOT=$PWD/plugins/flow FLOW_STATE=/tmp/x bash plugins/flow/scripts/install-cron.sh run lint`. The installed timers resolve the plugin through `installed_plugins.json`, so they pick up a new version at the next reinstall with no further step. The jobs are Claude-hosted whichever host orchestrates the pipeline, and that registry is Claude's user scope alone, so `flow@jakub` has to be installed at user scope (`claude plugin install`'s default) or the launcher resolves nothing. `install-cron.sh` runs every launcher-independent check before its first write and names that requirement when it fails.

`scripts/worktree-audit.sh` is ported from pstack (see `plugins/flow/NOTICE`); unlike grill's vendoring it is a fork, edit it freely.

The explicit `tools:` list on an agent def is load-bearing - a subagent without one can call Agent, and `implementer.md` relies on not having it.

### Delegation

Facts that go stale (model pricing, the Codex App Server protocol) carry an as-of date. Re-verify anything older than a quarter, and re-verify the host capability table on every CLI bump since both CLIs ship weekly. The developer-facing protocol lives in `plugins/flow/docs/DELEGATION.md` and `plugins/flow/src/delegation/`, validated against Codex CLI 0.152.0 as of 2026-09-01; `skills/delegate/SKILL.md` is the operating manual a session reads before its first bridge call, and the charter keeps three sentences pointing at it. Delegation requires Linux with cgroup v2 and a working systemd user manager because every provider runs in a transient scope; there is no other platform path.

`plugins/flow/capabilities.json` is the hand-maintained host capability table the issue stage's write-seat preflight reads through `delegation_doctor`. It is a plain file on purpose: editing it needs no rebuild. The doctor computes `hostCapabilities.drift` from the installed CLI version against the table's `verifiedAgainst` - `match`, `newer`, `older`, `unknown` - and the stage stops only on `older` or `unknown`; `newer` is a journal event asking for a re-check, because the table is biased false and a newer host can only have gained capabilities it does not yet claim.

The service is documented in `docs/DELEGATION.md` (protocol, store, approval fork, smokes) and `skills/delegate/SKILL.md` (what a session needs at call time); read the first before editing `src/delegation`. Three rules bind every edit. Every tool declares an `outputSchema` envelope, and `ERROR_KINDS` in `contracts.mjs` is the closed list the Codex smoke greps. An edit under `src/delegation`, a charter edit or a version bump is half a change until `npm run build` in `plugins/flow/deps` regenerates `dist/delegation.mjs` in the same commit; `scripts/smoke-bundle-drift.mjs` is the one script that needs `npm ci` there, and `smoke-delegation.mjs` (fake App Server, needs the containment prerequisites) and `smoke-claude-delegation.mjs` (fake Claude Code process) drive the committed bundle over MCP stdio with no account and no network. A delegated job is handed `seatPayload(charter)` verbatim, the same bytes a subagent gets, followed by the `<delegated-seat>` block; `src/delegation/instructions.mjs` throws at load if the charter carries no marker line, and the charter conformance smoke asserts the two payloads are equal. `agents/bridge.md` is the Claude transport seat for a bridge call and `scripts/smoke-bridge-seat.mjs` holds its tool list to exactly the delegate tools; Codex binds no transport seat, because `spawn_agent` narrows nothing.

## gripe

`plugins/gripe/` is first-party, no vendoring. Three layers: `lib/` (`store.mjs` owns SQLite and migrations, `context.mjs` derives repo and session identity, and `gate.mjs`, `failure.mjs`, and `checkpoint.mjs` own harness-neutral noise policy and bounded state), thin hook scripts under `hooks/scripts/`, and `bin/gripe` plus `bin/shim.mjs`, the CLI and the resolver that finds the installed plugin at exec time. Claude registrations live in `hooks/hooks.json`; Codex registrations live in `hooks/codex.json`. The design rationale with the measured claims is `docs/gripe/DESIGN.md`; the reader-side analysis method is the skill under `skills/gripe/`.

`bin/shim.mjs` is the copy at `~/.local/bin/gripe`: node builtins only, resolves the newest live install under this marketplace in either harness's cache at exec time, and carries one `// gripe-shim-epoch: <n>` line that bumps when shim behavior changes and never per release. `docs/gripe/DESIGN.md` holds the resolution rules and `scripts/smoke-shim.mjs` holds the contract; read both before touching it. Every hook validates `session_id` and `agent_id` before either reaches a filename, on both hosts.

Gripe's Codex checkpoint state is folded from structured PostToolUse events, never the unstable Codex transcript format. Codex does not identify the subagent actor on PostToolUse, so the checkpoint is parent-session state evaluated on main Stop only. Do not add a Codex SubagentStop checkpoint until the event stream can attribute its evidence. PostToolUse also has no reliable failure status (observed on 0.149.1: a Bash command that exited 7 supplied `tool_response: ""`), so Codex records tool-target repetition but does not run the Claude repeated-failure nudge. PermissionDenied and StopFailure remain Claude-only because Codex has no after-the-fact equivalents; a nearby event with different meaning is not a compatibility layer.

Filing must stay free: `gripe add` always exits 0 and never prompts. Any change that can make it exit non-zero or block on input breaks the contract every hook relies on. `scripts/collision-test.mjs` exercises concurrent writers against one database.

## grill

`plugins/grill/skills/` is vendored from https://github.com/mattpocock/skills (MIT), upstream plus four patches. Don't hand-edit the vendored files. A local change is a patch in `plugins/grill/patches/`, so a re-sync stays mechanical: copy the three upstream dirs over, `git apply` each patch in order, bump the SHA in `plugins/grill/NOTICE`. If a patch stops applying, regenerate it, and verify by applying the chain to a fresh upstream copy and diffing against `skills/` - identical or it is wrong.

The patches, in order: lowercase the doc-artifact filenames (`context.md`) and the skill's own reference docs, keeping `SKILL.md`, `AGENTS.md` and `CLAUDE.md` uppercase because the loaders find them by exact filename; route a `grilling` round through the structured question tool when it is in the tool list, and otherwise ask one question per turn with up to 4 numbered options, so the same vendored text works on Codex, with `grill-with-docs` composing through the Skill tool when there is one and by reading its two sibling `SKILL.md` files otherwise; strip the `context-map.md` mechanism out of `domain-modeling`, since we keep the map in a repo's `## Contexts` section and the prep stage forbids inferring "single context" from a missing map file; and let the model invoke `grill-with-docs` on both hosts (no `disable-model-invocation`, `allow_implicit_invocation: true` in its `agents/openai.yaml`). The capability check is inline in the vendored text because a model can read its own tool list.

Grill ships no Codex manifest: Codex finds `skills/*/SKILL.md` by itself, and `scripts/smoke-plugin-manifests.mjs` allows a skills-only plugin that shape.

Three skills is the minimal closure - `grill-with-docs` wraps `/grilling` using `/domain-modeling`. Upstream ships 36 across four buckets; carrying another one is a decision, not a default.

## unslop

`plugins/unslop/skills/unslop/SKILL.md` is vendored verbatim from Lauren Tan's pstack skill in `cursor/plugins` (MIT), no patches yet. If it ever needs one, follow the grill pattern and bump the SHA in `plugins/unslop/NOTICE`.

`hooks/scripts/inject-unslop.mjs` delivers the rules, not the skill description - "Must always apply" in frontmatter is advice the model follows unreliably. One script serves both harnesses in two modes. `session` runs on SessionStart and prints to stdout. `subagent` runs on SubagentStart, reads the hook JSON on stdin, and answers with `hookSpecificOutput.additionalContext`. Plugin-local wrappers live in `lib/rules.mjs`; source-aware skip policy lives in `lib/agent-selection.mjs`. Claude registrations use `hooks/hooks.json`, and Codex registrations use `hooks/codex.json`.

Each mode wraps the vendored body in its own plugin-local scoping note. The session note carves out conversation: the full ruleset for deliverables, rules 26-31 for technical explanations in chat, and the output style wins mechanical conflicts (em dashes, "harness"/"surface") in chat. The subagent note has no such carve-out, because a subagent has no conversational turn - everything it emits, including its report to the orchestrator, is a deliverable and gets the mechanical rules too. It does say the rules never license editing text the agent was asked to reproduce verbatim. Scoping changes go in these wrappers, never in a patch to the vendored file.

The subagent selection policy is the whole cost control: Claude `Explore` and the search fan-outs return file paths and would buy the ruleset once per agent, and `fork` already carries the session block in its copied context. Those skips are Claude-only, because each one is justified by a Claude mechanism; a Codex seat receives the rules whatever its name, until a Codex capture proves a skip safe there too. Everything else is on by default - the point is covering ad-hoc `general-purpose` and `claude` spawns that have no agent definition to carry the rules for them.

Watch the 10,000-character Claude hook stdout cap that forced flow's charter into two hooks. The subagent payload is JSON-wrapped, so it is the larger of the two: 7,786 bytes as of unslop 0.4.1, about 2KB of headroom. Codex's handler uses a 3,000-token inline context limit. A re-sync that grows `SKILL.md` past either bound eats or spills the rules. Measure after any vendor bump: `echo '{"agent_type":"claude"}' | node plugins/unslop/hooks/scripts/inject-unslop.mjs subagent claude | wc -c`.
