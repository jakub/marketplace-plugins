# marketplace-plugins - how to work in this repo

This is jakub's Claude Code plugin marketplace (README.md is the user-facing tour). The repo root holds the marketplace manifest at `.claude-plugin/marketplace.json` (marketplace name `jakub`) and shared docs; everything else is a self-contained plugin under `plugins/`. Install strings are `<plugin>@jakub`.

The charter you already have in context says how we build. This file is only about what's specific to editing the plugins themselves.

## Versions and publishing

Two version numbers move independently. Each plugin has its own `version` in `plugins/<name>/.claude-plugin/plugin.json`, mirrored in its entry in the marketplace manifest. A plugin with Codex support mirrors that version again in `.codex-plugin/plugin.json`, which since grill 0.5.0 is every plugin here. The manifest also has `metadata.version`, the catalog version, which bumps whenever the set of plugins or any listed version changes. A behavioral change to a dual-harness plugin is four edits: both plugin manifests, the marketplace entry, and the catalog version. `scripts/smoke-plugin-manifests.mjs` asserts the three plugin numbers agree, deriving them from the marketplace manifest so a release never edits the test.

Installs pull from the pinned GitHub clone, never from this working tree. To test a change: commit, push, then `claude plugin uninstall flow@jakub && claude plugin install flow@jakub`. Hook scripts can be exercised without a reinstall - `echo '<json>' | node plugins/flow/hooks/scripts/no-backlog-guard.mjs`.

Desktop and claude.ai bridge sessions load plugins from service-pushed snapshots with hooks stripped, so a bridge session never sees the charter or the guards; don't debug "the hook didn't fire" from one.

Adding a plugin: `plugins/<name>/` with a `.claude-plugin/plugin.json`, plus an entry in the manifest's `plugins` array with `"source": "./plugins/<name>"`. Plugins don't reach into each other's files - flow's `/flow:prep` uses `grill-with-docs` when it's installed and falls back to an inline grill otherwise, and that one-way, soft dependency is the model.

## flow

`plugins/flow/charter/charter.md` is hand-authored by jakub and is the source of truth. The SessionStart hooks deliver it to every session wrapped in `<flow-charter>` tags, which the global CLAUDE.md checks for. There are two hooks because Claude Code caps one hook's stdout at 10,000 characters and swaps anything larger for a 2KB preview plus a file path; `hooks/scripts/inject-charter.mjs` splits the file at the `## ` heading nearest the middle and prints a warning line if either half passes 9,000. Keep each half under that, or the session silently runs on a fragment while the presence check still passes. It's prose to a capable colleague, and it should stay that way. Every line costs context in every session, so anything that isn't true in every session goes somewhere else. The charter reaches the main session only - subagents get CLAUDE.md and the hooks, not the charter - which is why the implementer agent def restates the seat rules instead of assuming them.

The charter is host-neutral: it marks a role with `[[role:<id>]]` instead of naming a mechanism, and a third SessionStart hook delivers the host binding profile from `charter/profiles/<host>.md`, where each role gets bound. `scripts/smoke-charter-conformance.mjs` is the conformance and budget lint - it checks that both profiles bind every role the charter marks and that the charter halves and each profile hold under their byte caps. Profiles also ride delegated-seat instructions, carried through the rebuilt delegation bundle rather than read from a hook at delegation time.

Codex uses `hooks/codex.json` and one `inject-charter-codex.mjs` handler. Its context limit is large enough to keep the current charter inline, and one handler preserves order. Flow's shared `lib/hook-policy.mjs` owns protected-file and publication policy; Claude and Codex adapters own their different tool inputs and output decisions. Never return Claude's publication `ask` result to Codex: as of Codex CLI 0.149.1 (2026-08-26) it treats that unsupported value as a hook failure and lets the command continue, so its adapter must deny and direct the human to publish manually. If a later Codex gains `ask` support, that adapter can retire.

Doctrine lives in two places and no more. The charter holds what must be true in every session; the stage bodies hold the steps a stage executes. `commands/issue.md` is the last command that still holds its own steps. If something appears in both, delete one copy. The skill under `skills/flow/` holds what neither needs at runtime: setup, the doc stack, the ambient crons and hooks, the label contract, and the drift audit.

`/flow:issue` is the dynamic run: the conductor composes the fabric per issue inside the invariants in `issue.md`.

Prep and land are stages, not command bodies: `commands/prep.md` and `commands/land.md` are thin aliases and the steps live in `skills/prep-stage/` and `skills/land-stage/`. Each `SKILL.md` is the host-neutral prose, which names no host and marks its checkpoints with `[[gate:<id>]]` - ten for prep, 17 for land; `profiles/claude.md` and `profiles/codex.md` bind every one of those ids to a mechanism on that host, and both files carry every section even where the answer is "no difference". A profile may name a charter role in prose, but it never declares a `### role:` heading and a stage body never writes a `[[role:` marker: the role grammar belongs to the charter alone, and `smoke-charter-conformance.mjs` fails a stage that competes with it. The bindings that actually diverge are the human decisions (an interactive structured ask here, a suspended turn there), prep's two dialectic legs (each profile pins the native and the bridge model, so on a Codex host the outside opinion is a Claude model), and land's merge. On Claude the merge is a pre-approved `gh pr merge --squash` with no per-command prompt: the gate is the human's own `/flow:land` invocation plus the stage's CI-green and unresolved-thread checks, upstream of the command. On Codex it is a denied merge command plus the `land-merge.mjs` executor. An alias reads the Claude profile and then the skill; Codex reaches the same stage as the plugin-namespaced `prep-stage` or `land-stage` skill, and `agents/openai.yaml` sets `allow_implicit_invocation: false` because Codex 0.151 defaults it to true and a stage that merges, or that opens issues, must never start itself.

`scripts/smoke-stage-conformance.mjs` holds each stage's files together, and it finds the stages by structure rather than by name: a directory under `skills/` that holds `profiles/` is a stage, its name has to end in `-stage`, and its alias is `commands/<name minus the suffix>.md`. A stage added later is linted without an edit to the script. Per stage it checks that the gate ids and the profile headings are the same set both ways with nothing under a heading left empty, that `profiles/` holds exactly `claude.md` and `codex.md`, that `agents/openai.yaml` keeps implicit invocation off, and that the alias carries the routing sentence naming the Claude profile and then the skill, with an `allowed-tools` line string-equal to the one that profile declares. The banned-vocabulary list lives in this script and not in the shared engine, which stays vocabulary-blind on purpose: it covers the two families, the tools and call literals only one host has (`askuserquestion`, `apply_patch`, `explore`, `spawn_agent`, `fork_turns`, both `delegate_to_*` names) and the `$ARGUMENTS` placeholder, matched as whole tokens in any casing against the raw body, so a host name inside a code fence still fails. The engine in `scripts/lib/conformance.mjs` owns the marker grammar, the comment stripping, and the empty-section check, so the charter smoke gets all three for free. Fixtures come in two layers under `scripts/fixtures/stage-conformance/`, and that directory listing is the inventory, so read it rather than trusting a count written down here. A bare skill-and-profile pair goes through the engine alone, and each one breaks the marker grammar, a heading, or the parity between the two files. A miniature plugin root goes through the whole per-stage checker, and each one breaks something the engine never sees: the alias's routing sentence or its tool allowance, a host word in the shared body, the exact pair of profiles, or implicit invocation left on. Every case is valid but for the one defect it is named for and asserts the problem count, so a green run also proves the checker can still fail and fails for the reason claimed.

The Codex merge is a deterministic executor, not a checked command. `.flow/managed` is a committed marker that opts a repository into flow's merge enforcement; in a repository that has one, `publish-guard-codex.mjs` denies every merge command it can recognize and names `scripts/land-merge.mjs` in the denial, and in a repository without one it gates no merges at all. The executor takes a pull request number and nothing else; its authorization is the same as the Claude path's - the human explicitly asked to land and the stage's gates passed (an earlier release-sanction ceremony was retired 2026-08-29). It derives the host-qualified repository from the origin remote, reads the head SHA, state, draft flag and base branch from GitHub, refuses armed auto-merge or merge-queue states, and runs `gh pr merge` from an argv array with `--match-head-commit` pinned to the head it verified. The guard's command classification is a coarse tripwire whose only real requirement is that it never matches the executor's own invocation, and `scripts/smoke-release-path.mjs` asserts both halves against throwaway repositories with a fake `gh` injected in process.

The scheduled jobs are three files each: the prompt in `skills/flow/cron/<job>.md`, the allowlist in `scripts/flow-cron.mjs`, and the unit pair in `skills/flow/templates/systemd/`. A job's authority is the allowlist plus two mechanisms, never the prompt: git-guard's cron mode (deny-by-default git subcommands whenever FLOW_CRON_JOB is in the env, sanctions ignored) and `scripts/lint-actions.mjs`, the deterministic executor that alone performs the lint's worktree/branch mutations after re-deriving the safety conditions from fresh state; widening what a job may do is an edit to `flow-cron.mjs` and a version bump, and the prompt's "standing permissions" paragraph must match it. Test a prompt change without installing anything: `CLAUDE_PLUGIN_ROOT=$PWD/plugins/flow FLOW_STATE=/tmp/x bash plugins/flow/scripts/install-cron.sh run lint`. The installed timers resolve the plugin through `installed_plugins.json`, so they pick up a new version at the next reinstall with no further step.

`scripts/worktree-audit.sh` is ported from pstack (see `plugins/flow/NOTICE`); unlike grill's vendoring it is a fork, edit it freely.

Ad-hoc Workflow scripts are plain JavaScript: no TypeScript syntax, and no `Date.now()`, `Math.random()`, or argless `new Date()`, because they break resume.

Agent defs under `agents/` don't pin a model; the conductor sets model and effort at spawn. The explicit `tools:` list is load-bearing - a subagent without one can call Agent, and `implementer.md` relies on not having it.

Facts that go stale (model pricing, the Codex App Server protocol) carry an as-of date. Re-verify anything older than a quarter. The delegation contract lives in `plugins/flow/docs/DELEGATION.md` and `plugins/flow/src/delegation/app-server.mjs`, validated against Codex CLI 0.150.1 as of 2026-08-28. Linux delegation also requires cgroup v2 and a working systemd user manager because every provider runs in a transient scope. Two provider smokes cover the contract. `scripts/smoke-delegation.mjs` drives the service against a fake App Server. It requires Linux with the containment prerequisites, but needs no Codex, network, or installed dependencies. `scripts/smoke-claude-delegation.mjs` drives the Agent SDK against a fake Claude Code process. It needs the development dependencies from `npm ci`, but no Claude account or network. `scripts/smoke-bundle-drift.mjs` rebuilds `dist/delegation.mjs` from `src/delegation` and fails unless the committed bundle comes out byte-identical, which means it only works in a dev tree with `npm ci` already run in `plugins/flow/deps`. Every install runs the bundle and never the source, so an edit under `src/delegation` is half a change until `npm run build` in `plugins/flow/deps` regenerates `dist/delegation.mjs` and both go in the same commit.

## gripe

`plugins/gripe/` is first-party, no vendoring. Three layers: `lib/` (`store.mjs` owns SQLite and migrations, `context.mjs` derives repo and session identity, and `gate.mjs`, `failure.mjs`, and `checkpoint.mjs` own harness-neutral noise policy and bounded state), thin hook scripts under `hooks/scripts/`, and `bin/gripe` plus `bin/shim.mjs`, the CLI and the resolver that finds the installed plugin at exec time. Claude registrations live in `hooks/hooks.json`; Codex registrations live in `hooks/codex.json`. The design rationale with the measured claims is `docs/gripe/DESIGN.md`; the reader-side analysis method is the skill under `skills/gripe/`.

Gripe's Codex checkpoint state is folded from structured PostToolUse events, never the unstable Codex transcript format. Codex does not identify the subagent actor on PostToolUse, so the checkpoint is parent-session state evaluated on main Stop only. Do not add a Codex SubagentStop checkpoint until the event stream can attribute its evidence. As of Codex CLI 0.149.1, PostToolUse also has no reliable failure status: a Bash command that exited 7 supplied `tool_response: ""`. Codex therefore records tool-target repetition but does not run the Claude repeated-failure nudge. PermissionDenied and StopFailure remain Claude-only because Codex has no after-the-fact equivalents; a nearby event with different meaning is not a compatibility layer.

Filing must stay free: `gripe add` always exits 0 and never prompts. Any change that can make it exit non-zero or block on input breaks the contract every hook relies on. `scripts/collision-test.mjs` exercises concurrent writers against one database.

## grill

`plugins/grill/skills/` is vendored from https://github.com/mattpocock/skills (MIT), upstream plus five patches. Don't hand-edit the vendored files. A local change is a patch in `plugins/grill/patches/`, so a re-sync stays mechanical: copy the three upstream dirs over, `git apply` each patch in order, bump the SHA in `plugins/grill/NOTICE`. If a patch stops applying, regenerate it.

Patch 0001 lowercases the doc-artifact filenames (`context.md`) and the skill's own reference docs (`adr-format.md`, `context-format.md`) to match the rest of the repo. `SKILL.md`, `AGENTS.md`, and `CLAUDE.md` keep their uppercase names because the loaders find them by exact filename.

Patch 0002 routes a `grilling` round through the AskUserQuestion tool, up to 4 questions per call with selectable options, instead of upstream's numbered prose block with emoji headers. Upstream's design-tree and frontier model survives untouched; only the delivery changes. Verify a regenerated patch by applying both to a fresh upstream copy and diffing against `skills/` - identical or it is wrong.

Patch 0003 strips the `context-map.md` mechanism out of `domain-modeling`. We keep the map in a repo's `## Contexts` section instead, so the file never exists. It stays neutral on how many contexts a repo has, because the prep stage explicitly forbids inferring "single context" from a missing map file.

Patch 0005 makes the two Claude-only mechanisms conditional on the tool being there, so the same vendored text works on Codex. `grilling` routes a round through AskUserQuestion when that tool is in the list, and without it asks one question per turn with up to 4 numbered options, which keeps 0002's rhythm without the numbered essay 0002 exists to prevent. `grill-with-docs` composes through the Skill tool when there is one, and without it reads the two sibling `SKILL.md` files and follows both. The third hunk flips `allow_implicit_invocation` to true in `grill-with-docs/agents/openai.yaml`, the Codex half of the decision 0004 made on the Claude side by dropping `disable-model-invocation`. The check is inline in the vendored text because a model can read its own tool list; first-party per-host pointer files were considered and rejected as more files for no honesty gain.

Grill also ships `.codex-plugin/plugin.json`, with no `hooks` key and no MCP server, because Codex finds `skills/*/SKILL.md` by itself. `scripts/smoke-plugin-manifests.mjs` allows that shape - a Codex manifest may omit `hooks` when the plugin ships at least one skill, since an empty Codex manifest is a typo and not a plugin - and it asserts grill by name so a later edit cannot quietly drop it.

Three skills is the minimal closure - `grill-with-docs` wraps `/grilling` using `/domain-modeling`. Upstream ships 36 across four buckets; carrying another one is a decision, not a default.

## unslop

`plugins/unslop/skills/unslop/SKILL.md` is vendored verbatim from Lauren Tan's pstack skill in `cursor/plugins` (MIT), no patches yet. If it ever needs one, follow the grill pattern and bump the SHA in `plugins/unslop/NOTICE`.

`hooks/scripts/inject-unslop.mjs` delivers the rules, not the skill description - "Must always apply" in frontmatter is advice the model follows unreliably. One script serves both harnesses in two modes. `session` runs on SessionStart and prints to stdout. `subagent` runs on SubagentStart, reads the hook JSON on stdin, and answers with `hookSpecificOutput.additionalContext`. Plugin-local wrappers live in `lib/rules.mjs`; source-aware skip policy lives in `lib/agent-selection.mjs`. Claude registrations use `hooks/hooks.json`, and Codex registrations use `hooks/codex.json`.

Each mode wraps the vendored body in its own plugin-local scoping note. The session note carves out conversation: the full ruleset for deliverables, rules 26-31 for technical explanations in chat, and the output style wins mechanical conflicts (em dashes, "harness"/"surface") in chat. The subagent note has no such carve-out, because a subagent has no conversational turn - everything it emits, including its report to the conductor, is a deliverable and gets the mechanical rules too. It does say the rules never license editing text the agent was asked to reproduce verbatim. Scoping changes go in these wrappers, never in a patch to the vendored file.

The subagent selection policy is the whole cost control: Claude `Explore` and the search fan-outs return file paths and would buy the ruleset once per agent, and `fork` already carries the session block in its copied context. Those skips are Claude-only, because each one is justified by a Claude mechanism; a Codex seat receives the rules whatever its name, until a Codex capture proves a skip safe there too. Everything else is on by default - the point is covering ad-hoc `general-purpose` and `claude` spawns that have no agent definition to carry the rules for them.

Watch the 10,000-character Claude hook stdout cap that forced flow's charter into two hooks. The subagent payload is JSON-wrapped, so it is the larger of the two: 7,786 bytes as of unslop 0.4.1, about 2KB of headroom. Codex's handler uses a 3,000-token inline context limit. A re-sync that grows `SKILL.md` past either bound eats or spills the rules. Measure after any vendor bump: `echo '{"agent_type":"claude"}' | node plugins/unslop/hooks/scripts/inject-unslop.mjs subagent claude | wc -c`.
