# Cross-family delegation

This is the maintenance record for `plugins/flow/delegate/`. To call the tools, read `skills/delegate/SKILL.md` instead. Nothing here repeats it.

The Codex transport was checked on 2026-09-30 against Codex CLI 0.159.0 with a handshake that starts no model turn: `initialize`, `model/list`, `config/read`, `thread/start` with the `flow_delegation` profile and the thread config below, the thread's read-back, and `turn/steer` and `turn/interrupt` with no turn open. The turn notifications it folds come from the protocol schema that `codex app-server generate-ts --experimental --out <dir>` prints, and `thread/resume` is unchecked, because it refuses a thread that has never run a turn.

The Claude transport's handshake was checked on 2026-09-30 against Claude Code 2.1.284, also with no user message: `initialize` answers with the model catalog, `mcp_status` answers with an empty server list, and a CLI whose stdin closes before any user message exits 0 and prints nothing. The sandbox, the permission rules and the turn frames the Claude fold reads were checked on 2026-09-29 with real read-only jobs through the one-shot `claude -p --output-format stream-json`, which prints the same frames. The replayed user message, the `tools`, `mcp_servers` and `plugins` fields of the `system/init` frame, and the `interrupt` control request come from the Agent SDK's type definitions and have not been seen in a live turn.

No model turn has run through either transport yet. `node plugins/flow/scripts/smoke-delegate.mjs` proves the contract against fake providers in about 30 seconds, most of it one job running out its 30-second budget.

## What each file owns

The server is eight files that need Node 22 or later and Node built-ins only. There is no build step, no bundle and no npm dependency, so an edit takes effect on the next server start.

| File | Owns |
| --- | --- |
| `main.mjs` | The entry. `mcp --host claude\|codex` serves MCP on stdio. `run --job <id>` runs one job. |
| `server.mjs` | MCP over stdio, by hand: `initialize`, `ping`, `tools/list`, `tools/call`, `notifications/cancelled`, and one outbound request, `roots/list`. |
| `jobs.mjs` | Admission, the job directory, the write lease, the runner spawn, waiting, cancel, reconciliation and the 14-day prune. |
| `codex-app-server.mjs` | The Codex target: a JSON-RPC client of `codex app-server --stdio`, the catalog check, the thread config and the `flow_delegation` profile, the read-back before the prompt, the declined approvals, and the fold from notifications to an outcome. |
| `claude-control.mjs` | The Claude target: a client of the `claude -p` stream-json control channel, its argv and sandbox settings, the catalog check and the MCP read-back before the prompt, the `system/init` check after it, and the fold from frames to an outcome. |
| `providers.mjs` | What both targets share: the PATH lookup, the provider environment, version and sign-in, the catalog rule, and the outcome check. |
| `runner.mjs` | The detached process that drives one job through its target's session, and `delegatedInstructions`, which builds the seat block. |
| `schema.mjs` | The JSON Schema subset a structured answer is checked against: `schemaProblem` at admission, and `checkAnswer`, which runs `validate` in a child process before success. |

`bin/flow-delegate` is the Codex launcher. Codex passes a plugin MCP server's command to the launcher without expanding variables, so a command on PATH is the only way to start the server in the thread's project directory. The launcher reads `--flow-version`, imports `$CODEX_HOME/plugins/cache/jakub/flow/<version>/delegate/main.mjs` into its own process, and exits 1 naming that path when the file is missing. `scripts/install-delegate.mjs install` copies the launcher to `~/.local/bin/flow-delegate` when that copy is missing or differs. Codex starts MCP servers before SessionStart hooks run, so the flow skill's `setup` runs the installer once, and the Codex SessionStart hook keeps the copy current after that.

## Contracts that bind an edit

- The tools declare an `inputSchema` and no `outputSchema`, so no client validates `structuredContent`. Every result is `{ok, job?, error?}`, and the doctor adds its own fields. The same object goes out twice: as `structuredContent`, and as JSON text whose first line is `summary`.
- `error.kind` is the closed set listed in the delegate skill. Add a new kind to that list in the same commit as the code.
- A delegated seat's instructions are `seatPayload(charter.md)`, byte for byte, read from `charter/charter.md` when the job runs, then the `<delegated-seat>` block. Both are written to `seat.md`. On Codex they go in the thread's `developerInstructions`, and `turn/start` carries the caller's prompt alone. On Claude they go in through `--append-system-prompt-file`, and the one user message carries the caller's prompt alone. No rule rides in caller prose. `smoke-delegate.mjs` checks the bytes.
- No Codex prompt goes out before the read-back. `turn/start` is sent only after the thread reports `activePermissionProfile.id` equal to `flow_delegation`, a `model` equal to the requested one, and an MCP inventory in which every server reads `disabled` with no tools. A failed read-back fails the job `ISOLATION` or `MODEL_MISMATCH`, and the envelope says `promptSent: false`.
- No Claude prompt goes out before the read-back either. The user message is written only after `initialize` has answered and `mcp_status` has reported no server, and it sets `client_composed: true`. A `system/init` frame that names a tool outside the requested set, any MCP server or any plugin, or that lacks one of those lists, interrupts the turn, and the job fails `ISOLATION`.
- When a provider's catalog lists the requested model, the requested effort must be one the catalog lists for it. Otherwise the job fails `BAD_MODEL` before the prompt, and on Codex before the thread. An id the catalog does not list is admitted, and the envelope says `catalog: "absent"`. `listing` in `providers.mjs` is the one rule both targets call.
- The model that answers is the model requested. On Codex the thread's `model` must equal the request. On Claude the init frame and every assistant frame must name the catalog's `resolvedModel`, or the init frame's own model when the catalog does not list the id. A mismatch interrupts the turn and fails `MODEL_MISMATCH`.
- Provider stderr and stack traces go to `stderr.txt` and `server.log`, never into a tool result. An error message the provider put in its own output may appear, clipped to 500 characters.
- An outcome needs native proof. Success needs a terminal event (`turn/completed` with status `completed` from Codex, a `result` frame from Claude) and an answer. A running job whose runner is gone reads `unknown` with `RUNNER_LOST`.
- A job with a schema succeeds only when its answer conforms to it, checked by `schema.mjs` and not taken on trust from either provider, since Codex narrows a schema outside its subset without saying so. A schema is admitted only when every keyword in it is one `schema.mjs` checks or an annotation, so no admitted schema is checked in part. A new keyword goes into both of its functions at once. The check runs in a child process that is killed after 10 seconds, and an answer it did not finish checking fails `SCHEMA_OUTPUT`. Admission bounds the schema but not the check: shared references can multiply the work at every level, and a pattern can backtrack without end. The runner holds the job and its lease until the outcome is written, so the check must not run in the runner itself.

## Roots

A root comes from the host, never from the call or the environment. On Claude the roots are the client's `roots/list` answer and `CLAUDE_PROJECT_DIR`, asked for again on every call. On Codex the one root is `process.cwd()` when it equals `git rev-parse --show-toplevel` and is not `$HOME`. Otherwise there is no root and every start fails `NO_ROOTS`.

A job's `cwd` and its Git top level must both resolve, through `realpath`, inside a root. Inherited `PWD`, `CODEX_PROJECT_DIR`, `GIT_DIR` and `GIT_WORK_TREE` are ignored: the server runs Git with every `GIT_*` variable removed and with `GIT_CONFIG_GLOBAL=/dev/null` and `GIT_CONFIG_NOSYSTEM=1`. A job is visible only to a server for the same host whose roots contain the job's `cwd`. The state directory is shared by every session, so a job id from another workspace reads `JOB_NOT_FOUND`.

## Job state

The state directory is `${FLOW_DELEGATION_STATE_DIR:-${XDG_STATE_HOME:-~/.local/state}/flow}`. It holds `jobs/<uuid>/`, `leases/` and `server.log`. A job directory holds `job.json`, `prompt.txt`, `schema.json` when a schema applies, `seat.md`, `events.jsonl`, `stderr.txt` and a private `tmp/` that becomes the provider's `TMPDIR`.

Writers replace `job.json` only by rename, so a reader sees the old record or the new one. While a runner lives, it is the only writer of its job. The server writes a record to create it, to cancel a job no runner has claimed, and to settle a job whose runner is gone. A `claim` file decides who moves a queued job. It is linked into place already holding its holder's pid and start token, so a late runner, a cancel and a lease takeover never both act on one job, and a job whose holder died can still be settled. A `cancel` file asks a running job to stop. When a server starts, it removes terminal job directories older than 14 days.

A write job holds `leases/<sha256 of its worktree's real path>/`, a directory holding one file named for the job. The lease is built under a private name and renamed into place whole, and `rename(2)` onto a directory that is not empty fails, so two admissions cannot both take it. It is keyed on the job's Git top level rather than its `cwd`, so two write jobs in different subdirectories of one worktree still collide. Before a lease is taken over, its holder is reconciled: a job queued past its minute is claimed and settled, so its runner can never start it later, and a running job whose runner is gone has its provider group killed and reads `unknown`. A lease whose holder has ended is then taken over by moving out the file under that job's own name and removing the directory only if it is then empty. A lease that changed hands in between has a different file name, so no release and no takeover can remove it. Read-only jobs take no lease.

## The runner

The server spawns `node main.mjs run --job <id>` detached, with its stdio closed, so a job outlives the server and the session. The runner records its pid and its start time (field 22 of `/proc/<pid>/stat`) in `job.json`. A reader compares both to tell a live runner from a recycled pid.

The runner drives the job through a session that the target's transport opens. The transport spawns the provider in its own process group, with a fixed set of environment variables, and hands the child to the runner before anything can signal it. The runner records the group's leader pid and start time. A recorded group is signalled only while its leader is that process, or while the leader is gone and members remain, which the kernel keeps unambiguous by never reusing an id a live group carries. A leader pid that names a process with another start time means the id was reused, and nothing is sent, however long after the job a reader settles it. It appends every stdout line to `events.jsonl` unchanged, and the session folds the lines that parse as JSON. Three things stop a job: its time budget, 420 seconds with no stdout line, and the `cancel` file, which the runner polls every 500 ms. A stop first sends the provider's own interrupt, then `SIGTERM` to the group and `SIGKILL` 10 seconds later. On Codex the interrupt is `turn/interrupt`, and on Claude it is the `interrupt` control request. Each gets 10 seconds to answer. `events.jsonl` records the stop as a `flow.stop` line and the interrupt's answer as a `flow.interrupt` line. The runner records `promptSent` in `job.json` the moment the prompt leaves it, and `catalog` once the session opens. It records `isolation`, what the live session read back, once the session has it: when the Codex thread opens, or at the Claude `system/init` frame. It writes the provider's thread id as soon as the session knows it, so a running job can be steered: a `continue` naming it stops the job through the `cancel` file, waits up to 15 seconds for it to end, and starts the continuation on the same thread. A job with no thread yet is refused and left running. When a turn ends, with `turn/completed` on Codex or the first `result` frame on Claude, the runner closes the provider's stdin, and the provider exits. When the provider exits, the runner kills whatever is left in its group, releases the lease, and then writes the outcome. A native success stands even when a stop raced it. A refusal, a model swap or a failed isolation read-back that the provider already showed outranks the stop that followed it.

## Why each provider runs the way it does

The Codex thread config lives in `codex-app-server.mjs`, and the Claude argv and settings in `claude-control.mjs`. These choices are the ones an edit is most likely to undo.

- Codex runs as `codex app-server --stdio`, not `codex exec`. The App Server opens a thread before it takes a prompt, so flow can configure the thread and read it back first. `codex exec` sends the prompt in the same call that creates the session. The handshake is `initialize` with `experimentalApi: true`, `model/list`, `config/read`, then `thread/start`, or `thread/resume` for a continuation.
- `model/list` is read with `includeHidden: true`, so a hidden model the account can use counts as listed. The effort check runs before `config/read`, so a refused effort opens no thread.
- The `flow_delegation` permission profile is the containment. On 0.159.0 the built-in `:read-only` and `:workspace` profiles can read `~/.ssh`, `~/.config/gh/hosts.yml`, `~/.codex/auth.json` and `~/.claude/.credentials.json`. The profile grants read on `:minimal`, the worktree, the real paths of its Git directory and common directory, and the Codex executable. It grants write on the job's `tmp/`. A write job also gets write on the worktree, with `.git`, `.agents` and `.codex` kept read-only. Network is off.
- The thread names the profile twice: as `permissions`, and as `default_permissions` in its config. In a scratch home, a thread config that defined `[permissions]` without `default_permissions` made `mcpServerStatus/list` fail with a config reload error.
- Codex runs every shell command by re-executing its own binary inside bubblewrap. Without read on that binary, every command fails with `bwrap: execvp ...: No such file or directory`, and the turn still succeeds (openai/codex#29049). The grant is the real path of `/proc/<pid>/exe`, read once `initialize` answers, so a mise shim that execs in place already names the real binary. The grant also covers the PATH entry that started Codex, that entry's real path, and the npm package root when either path runs through `node_modules`.
- The App Server has no `--ignore-user-config`, so it loads `$CODEX_HOME/config.toml` and any trusted project layer. The thread config turns off `features.plugins`, `features.apps`, `features.hooks`, `features.memories`, `features.multi_agent`, `features.multi_agent_v2`, `features.browser_use`, `features.computer_use` and `features.image_generation`. It also turns off `memories.use_memories` and `memories.generate_memories`, and disables `apps._default`.
- Every MCP server that `config/read` names, in the effective config or in a layer Codex loaded, is disabled in the thread config. A layer that `config/read` reports with a `disabledReason`, such as an untrusted project, contributes no names: on 0.159.0, disabling a name that no loaded layer defines fails `thread/start` with "invalid transport". If the thread loads such a layer anyway, the read-back finds its servers.
- `config/read` takes the job's `cwd`, not the worktree, so it sees the same project layers as a thread started in a subdirectory.
- The read-back checks the live thread, not the layers flow built it from: `activePermissionProfile.id`, the thread's `model`, and `mcpServerStatus/list` for the thread, at most ten pages. `allowProviderModelFallback: false` asks Codex not to substitute a model, and the model check proves it did not.
- `approvalPolicy: "never"` means no approval request should arrive. One that does gets its method's decline: `decline` for `item/commandExecution/requestApproval` and `item/fileChange/requestApproval`, `{permissions: {}, scope: "turn"}` for `item/permissions/requestApproval`, and `denied` for `applyPatchApproval` and `execCommandApproval`. Any other server request gets JSON-RPC error `-32601`. A request whose method names an approval fails the job `APPROVAL_REQUIRED` once the turn ends, with the answer kept.
- Claude runs as `claude -p --input-format stream-json --output-format stream-json --verbose --replay-user-messages`, the channel the Agent SDK speaks. The CLI opens its session before it takes a prompt, so flow can read the session back first. A one-shot `claude -p` takes its prompt in the same call that opens the session.
- The control messages flow sends are the ones behind public Agent SDK methods: `initialize` (`initializationResult`), `mcp_status` (`mcpServerStatus`), `interrupt` (`interrupt`), and user messages (`streamInput`). The CLI has to keep them working for every SDK version in use. Each control request is `{type: "control_request", request_id, request: {subtype}}`, and its answer is a `control_response` frame with the same `request_id`.
- `client_composed: true` on the user message stops the CLI from expanding an `@path` mention or running a slash command in a prompt that another model wrote.
- A control request from the CLI gets an error response. The argv names no `--permission-prompt-tool`, so under `dontAsk` the CLI decides every permission itself. A `can_use_tool` request that arrives anyway fails the job `APPROVAL_REQUIRED` once the turn ends, with the answer kept.
- The Claude catalog lookup matches the requested id against an entry's `value` or its `resolvedModel`, ignoring case and a `[1m]` suffix, and prefers the `value` match. On 2.1.284, `opus` resolves to `claude-opus-5-5`, `haiku` lists no effort levels and so fails `BAD_MODEL` at any effort, and `fable` is not a `value`, so it runs with `catalog: "absent"`.
- `claude -p --setting-sources "" --strict-mcp-config` loads no settings file, plugin, skill or MCP server. Settings passed with `--settings` still apply, and they carry the containment. `mcp_status` and the `system/init` frame check the live session for MCP servers and plugins.
- Claude's sandbox covers Bash only. `Read`, `Grep` and `Glob` use permission rules, so the credential paths and `/proc` appear twice: as `sandbox.filesystem.denyRead` for Bash, and as `Read(//path)` deny rules for the file tools. `Edit` is allowed inside the worktree on a write job and nowhere else.
- The sandbox masks a provider executable only when its real path names the provider. On this machine `codex` is a mise shim that resolves to `/usr/bin/mise`, and masking it replaced mise with `/dev/null` inside the sandbox, which broke `node` and every tool mise serves.
- `--permission-mode dontAsk --permission-prompts none` turns every would-be prompt into a denial. The result frame lists the denials, and a turn with any fails `APPROVAL_REQUIRED` with its answer kept.
- The Claude environment carries `CLAUDE_CODE_DISABLE_REFUSAL_FALLBACK=1` and `CLAUDE_CODE_NO_MODEL_FALLBACK=1`. Neither is public API, so the fold also checks the model on the `system/init` frame and on every assistant frame, ignoring `<synthetic>` and a `[1m]` suffix. `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1` keeps a job out of the human's project memory.
- A provider sees `PATH`, `HOME`, `USER`, `LOGNAME`, `SHELL`, `LANG`, `LANGUAGE`, `TERM`, `TZ`, `CODEX_HOME`, `CLAUDE_CONFIG_DIR`, `XDG_*` and `LC_*`, plus `TMPDIR`, `FLOW_DELEGATION_DEPTH=1` and `FLOW_DELEGATION_JOB`. A server that finds `FLOW_DELEGATION_DEPTH` in its own environment refuses to start a job, so delegation is one hop deep.
- Only absolute PATH entries count when the server looks for a provider, so a worktree can never supply the executable.

## Limits accepted on purpose

- A provider that double-forks out of its process group survives cancel and can outlive the lease. Every recorded job to date was read-only. If a write job ever needs proof of death, run the provider under a systemd scope and read the scope's cgroup before releasing the lease.
- A delegated Codex thread loads the human's config. A feature that a later Codex release turns on by default reaches delegated threads until it joins the thread config's list. The read-back covers the profile, the model and MCP servers, and nothing else.
- The App Server fields flow depends on (`permissions`, `runtimeWorkspaceRoots`, `allowProviderModelFallback` and `activePermissionProfile`) appear only in the `--experimental` schema. On a Codex bump, compare them with the output of `codex app-server generate-ts --experimental --out <dir>`.
- Codex reports the thread's model once, when the thread opens. A `model/rerouted` notification during a turn is journaled and not checked.
- The Claude tool list first appears in the `system/init` frame, after the prompt has gone out. The check still stops the turn before any tool result exists. If a Claude Code release lists a tool that `--tools` did not name, every Claude job fails `ISOLATION` until that tool joins the requested set in `claude-control.mjs`.
- The Claude control channel has no published specification. On a Claude Code bump, compare `initialize`, `mcp_status`, `interrupt` and the user message with the Agent SDK's `sdk.d.ts`.
- A job refused `BAD_MODEL`, or refused before the catalog was read, has `catalog: null`. The `BAD_MODEL` details name the efforts the catalog lists.
- A Codex write job cannot commit, because its Git metadata is read-only. The orchestrator commits a delegated writer's work.
- Flow's PreToolUse hooks do not load inside a delegated job. A write job is confined to its worktree and nothing narrower, so it can edit a lockfile or an `.env` file there.
